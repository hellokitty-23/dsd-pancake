# DSD Pancake 产品计划

> 状态：评审中
>
> 本文定义产品目标、边界和验收条件，不替代具体的架构说明或实现设计。除非另有明确决定，本文中的“DSH”均指用户已在本机独立安装的 DeepSeek Harness Web 服务。

## 1. 产品定位

DSD Pancake 是一个 macOS 原生薄壳（只负责本地启动、窗口和系统交互，不承载 DSH 业务功能）。它让用户从 Dock、Finder 或 Spotlight 打开一个独立 App，在其中使用原有的 DSH Web UI。

产品的核心承诺是：

```text
DSH 的安装、数据、功能与更新路径  ←→  始终独立
                                      │
                                      ▼
                        DSD Pancake 只负责启动和展示
                                      │
                                      ▼
                         http://127.0.0.1:3080/
```

换言之，DSD Pancake 不是 DSH 的发行包、分支版本或替代品。DSH 继续由用户按原有方式安装和更新；App 每次启动时使用的都是该独立安装的当前版本。

### 1.1 已确认的产品决策

- App 不调起 `Terminal.app`，而是在自身进程内以受控子进程运行用户已有的 DSH 启动入口；用户不会看到额外的终端窗口。
- App 只在固定地址没有兼容 DSH 服务时，才调用已配置的启动入口（示例：`dsh web`）；已有服务只复用，不接管。
- `⌘Q` 表示退出整个 DSD Pancake 会话。若本会话启动了 DSH，App 在清晰确认后停止该次服务；若只是复用外部服务，则只退出 App。
- 窗口左上角的关闭按钮只隐藏窗口，不等同于 `⌘Q`，以免一次误点中断正在使用的本地服务。

## 2. 要解决的问题

直接在浏览器打开 DSH 虽然可用，但容易混入普通网页工作流：地址栏、标签页、外部跳转、错误关闭窗口等操作都可能造成干扰或误触。用户希望获得以下体验：

1. 打开一个固定用途的 macOS App，而非寻找浏览器标签页；
2. App 在需要时自动运行原本的 DSH 启动命令，例如 `dsh web`；
3. 服务就绪后，在 App 内打开固定地址 `http://127.0.0.1:3080/`；
4. 不因包装 App 而失去 DSH 的正常升级能力；
5. 退出 App 时只停止由该次 App 启动的服务，不误伤用户在终端或其他位置启动的 DSH；
6. 让浏览器层面的误操作更难发生，而不篡改 DSH 自己的网页功能。

## 3. 目标用户与使用场景

目标用户是已经能在本机运行 DSH，并希望把它作为长期桌面工具使用的人。

典型路径如下：

```text
用户打开 DSD Pancake.app
          │
          ├─ 3080 上已有兼容的 DSH 服务
          │      └─ 直接复用服务并显示网页
          │
          └─ 服务未运行
                 └─ 调用用户原有的启动入口
                         └─ 等待服务就绪
                                 └─ 在原生窗口中显示 DSH
```

用户仍可在终端中独立运行、停止或升级 DSH。App 对这种外部服务只做连接，不取得其生命周期控制权。

## 4. 产品原则

### 4.1 DSH 独立性优先

- 不把 DSH、Node.js、用户插件、用户配置或用户数据复制进 `.app`；
- 不修改用户现有的 DSH 安装目录、配置文件、数据目录或更新源；
- 不要求 DSH 为桌面壳使用某个固定版本；
- App 与 DSH 可以独立更新、独立回退、独立排障；
- App 不自动升级 DSH。若未来提供更新辅助，必须是用户主动发起、可见、可取消且复用 DSH 原有更新机制的操作。

### 4.2 只管理自己创建的进程

进程归属（某个进程是否由当前 App 会话直接创建且仍可验证）是退出行为的唯一依据，不能只看端口是否可用或命令行文字是否相似。

- 启动前已有的服务属于 external（外部已有）服务：可连接，不可停止；
- 当前 App 直接启动且持续验证归属的服务属于 owned（本次拥有）服务：可在用户明确退出时正常停止；
- 如果归属无法验证，默认不停止；
- 禁止使用 `pkill -f` 等全局模式匹配方式结束 DSH。

### 4.3 包装网页，不补丁网页

App 使用 `WKWebView`（macOS 系统网页容器）展示 DSH，但不依赖网页 DOM（文档对象模型，即网页内部元素结构）来改按钮、读取对话或拦截业务操作。这样 DSH 更新网页界面后，桌面壳仍保持兼容。

防误触优先放在原生壳层解决，例如：没有地址栏和标签页、受限的外部跳转、关闭确认和可选的操作锁。真正的业务级确认应由 DSH 自己提供稳定能力，而不是由 App 猜测网页元素含义。

### 4.4 可理解、可恢复

用户应始终能理解 App 目前是在连接现有服务，还是在运行自己启动的服务；服务失败、地址被占用、启动命令失效或服务重启时，应有明确状态和可执行的恢复操作。

## 5. 第一版范围

| 能力 | 第一版行为 |
| --- | --- |
| 固定入口 | 在 App 内展示 `http://127.0.0.1:3080/`，不提供通用地址栏或标签页。 |
| 服务探测 | 启动时以有界的 HTTP 探测确认目标服务是否是可兼容的 DSH，而非仅凭端口可连接。 |
| 启动服务 | 没有可用服务时，以结构化的可配置启动入口运行用户已有的 DSH；默认示例为 `dsh web`。 |
| 启动环境 | 支持保存可执行文件路径、参数、工作目录及必要环境信息，处理图形 App 与终端 `PATH` 不同的问题。 |
| 就绪等待 | 在有限时间内等待 DSH 真实就绪；失败时展示诊断信息、有限日志和“重试”入口。 |
| 网页承载 | 使用持久 `WKWebView` 保留网页会话；同源页面留在 App 内。 |
| 外部导航 | 非本机 DSH 的链接默认交给系统浏览器，必要时先向用户说明。 |
| 退出语义 | 关闭窗口不默认杀掉服务；`⌘Q` 退出时，仅在服务归属为 owned 时确认并停止它。 |
| 状态与日志 | 显示“连接现有服务”“正在启动”“已就绪”“启动失败”等明确状态，并提供不会泄露网页内容的本地诊断信息。 |
| DSH 更新兼容 | 不捆绑 DSH；用户通过原有命令更新后，下一次启动自然使用更新后的 DSH。 |

## 6. 明确不做的事

第一版不包含以下能力：

- 重新实现 DSH 的聊天、任务、模型、账户或插件功能；
- 内置 DSH、Node.js、npm 或另一份 DSH 配置；
- 在没有用户动作时下载、更新、替换或重启 DSH；
- 把网页内容、Cookie、对话、输入内容或工作区数据同步到原生层；
- 向网页暴露任意 Shell、`eval`、命令执行或进程控制桥；
- 用全局扫描或模糊命令匹配接管、停止外部 DSH；
- 通过注入 JavaScript 给 DSH 页面中的特定按钮“打补丁”；
- 为远程地址提供通用浏览器能力。

## 7. 关键交互与生命周期

### 7.1 首次配置

App 首次无法可靠定位 DSH 时，应进入简洁的配置流程，而不是猜测用户终端环境。用户配置的是启动入口，而不是让 App 安装 DSH：

```text
DSH 可执行文件：/绝对路径/到/dsh
参数：web
工作目录：可选
```

实现层应以“可执行文件 + 参数数组”的结构保存和启动，避免把用户输入拼成经由 Shell 解释的字符串。若用户已有稳定的包装脚本，应由用户明确选择该脚本作为启动入口。

### 7.2 正常打开

1. App 检查固定本机地址是否存在兼容服务。
2. 若存在，标记为 external，直接加载网页。
3. 若不存在，创建新的 DSH 子进程并记录必要的归属信息。
4. App 以有限重试等待 DSH 就绪，成功后加载网页。
5. 若启动失败，展示原因、有限日志和“重试”或“打开配置”操作；不得无限重启。

### 7.3 服务中断与重连

若网页已加载后服务被外部停止或更新重启，App 显示可恢复状态，并允许用户重新连接或在适用时重新启动本次 owned 服务。它不能因为端口暂时不可用就推断自己有权停止或接管其他进程。

### 7.4 关闭窗口与退出 App

| 用户动作 | 预期行为 |
| --- | --- |
| 点击窗口红色关闭按钮 | 关闭或隐藏窗口，不默认停止本次 DSH；再次从 Dock 打开时恢复会话。 |
| 再次打开 App | 显示已有窗口或当前会话，避免重复启动服务。 |
| `⌘Q` / 菜单“退出” | 若存在 owned 服务，明确告知将停止该服务并允许取消；确认后按正常终止流程回收该进程及其子进程组。 |
| `⌘Q` / 菜单“退出”且仅连接 external 服务 | 直接退出 App，不停止该服务。 |
| App 异常退出 | 下次启动不得假定旧服务仍属于当前 App；只有重新验证后才可将其作为可连接服务使用。 |

## 8. DSH 更新策略

DSH 的升级与 DSD Pancake 的发布必须解耦。

```text
用户用原有方式更新 DSH
        │
        ▼
独立安装位置中的 dsh 被替换或升级
        │
        ▼
下次打开 DSD Pancake
        │
        ▼
App 调用同一启动入口，运行新版 DSH
```

验收时必须验证：在不重新打包、不修改 DSD Pancake 的前提下，用户更新 DSH 后，App 能启动并展示更新后的版本。若新版 DSH 改变启动参数、健康探测契约或本机地址，则应视为兼容性问题并提供清晰配置或升级路径，而不是悄悄回退到内置副本。

## 9. 防误触设计

### 必备保护

- 固定本机地址，无地址栏、书签栏和多标签页；
- 同源导航保留在 App 内；
- 外部链接不静默替换当前 DSH 页面；
- 对真正退出与停止 owned 服务给出清晰确认；
- 启动失败和重连状态不会伪装成正常网页。

### 可选增强

可在后续版本增加原生“操作锁”：锁定时用 App 层遮罩阻止对网页的点击和键盘输入，解锁后才允许操作。该能力不读取网页内容、不识别具体按钮，因此不会因 DSH 更新页面结构而失效。

## 10. 成功指标与验收条件

产品是否完成不能只以“窗口能打开”判断，至少应满足以下可观察结果：

1. 用户从 Finder 或 Dock 打开 App 后，不需要手动先打开 Terminal.app，即可在服务就绪后进入 DSH。
2. 当 `127.0.0.1:3080` 已有用户手动启动的兼容 DSH 时，App 不会创建第二个实例，退出时也不会停止该实例。
3. 当服务由 App 启动时，`⌘Q` 的确认操作只停止该次 App 创建且仍可验证归属的进程。
4. 当启动命令不可用、端口被非兼容服务占用或 DSH 启动失败时，用户能看到准确状态并恢复，而不是得到空白页面或无限加载。
5. 用户按原有流程更新 DSH 后，无须重新安装 DSD Pancake，即可由 App 启动更新后的 DSH。
6. App 不向 DSH 网页注入依赖页面结构的业务逻辑，也不读取会话或用户内容。
7. 关闭窗口、重新打开窗口、服务重启和 App 退出等路径不会造成未声明的重复实例或误杀外部进程。

## 11. 交付阶段

| 阶段 | 目标 | 交付物 |
| --- | --- | --- |
| 阶段 0：环境确认 | 确认用户实际 DSH 启动命令、安装位置、工作目录、依赖环境及更新方式。 | 启动入口配置约定与兼容性清单。 |
| 阶段 1：最小可用壳 | 实现服务探测、受控启动、就绪等待、固定 `WKWebView`、external/owned 区分和安全退出。 | 可本地构建的 macOS App 与基础验证。 |
| 阶段 2：可恢复性 | 补齐失败状态、重试、有限日志、单实例处理和断线后的重连体验。 | 异常路径验证记录。 |
| 阶段 3：防误触与打磨 | 完善外链策略、退出确认、窗口行为和可选操作锁。 | 用户可见交互说明与回归验证。 |
| 阶段 4：发布准备 | 完善签名、打包、安装说明、故障排查及 DSH 更新兼容性说明。 | 可分发的 `.app` / 安装包和用户文档。 |

## 12. 实施前待确认项

以下事实应在实现启动器前从用户的真实环境中确认，不能由 App 猜测：

1. 当前启动 DSH 的完整命令，以及是否就是 `dsh web`；
2. `dsh` 的实际可执行文件位置，以及是否依赖 shell profile、Node 版本管理器或虚拟环境；
3. 是否必须从特定工作目录启动；
4. DSH 可用于稳定判定“已就绪”的 HTTP 契约；
5. 用户希望关闭窗口时隐藏还是退出，以及是否希望 App 退出后停止本次服务；
6. 对外部链接、更新提示和操作锁的具体偏好。

这些信息明确后，架构设计应围绕真实启动入口展开；产品不能为了简化实现而新建、复制或接管一套 DSH。
